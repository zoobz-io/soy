# Work-Queue Claim

*Recipe: Claim a batch of pending jobs for processing without two workers grabbing the same row.*

The canonical PostgreSQL pattern is `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)`.
The inner `SELECT` locks a batch of pending rows and skips any a sibling worker already holds; the
outer `UPDATE` flips their status and returns them. Soy builds the whole statement — no raw SQL.

```go
type Job struct {
    ID        int64     `db:"id" type:"bigserial primary key"`
    Status    string    `db:"status" type:"text"`
    CreatedAt time.Time `db:"created_at" type:"timestamptz default now()"`
}

jobs, _ := soy.New[Job](db, "jobs", postgres.New())

// The subquery: oldest pending rows, locked, skipping rows other workers hold.
pending := jobs.Query().Fields("id").
    Where("status", "=", "pending_status").
    OrderBy("created_at", "asc").
    LimitParam("batch").
    ForUpdate().
    SkipLocked()

// The claim: flip status on those rows, return the whole batch.
claimed, err := jobs.Modify().
    Set("status", "processing_status").
    WhereInSubquery("id", pending).
    ExecMany(ctx, map[string]any{
        "processing_status":  "processing",
        "sq1_pending_status": "pending",
        "sq1_batch":          100,
    })
```

Use `ExecMany` (returns `[]*T`), not `Exec`. A batch claim updates more than one row,
and `Exec` errors with *"expected exactly one row updated, found multiple"* — it is
built for single-row updates. `ExecMany` returns every claimed row.

Rendered SQL:

```sql
UPDATE "jobs" SET "status" = :processing_status
WHERE "id" IN (
    SELECT "id" FROM "jobs" WHERE "status" = :sq1_pending_status
    ORDER BY "created_at" ASC LIMIT :sq1_batch
    FOR UPDATE SKIP LOCKED
) RETURNING "id", "status", "created_at"
```

## Parameter naming — the `sq1_` prefix

The renderer prefixes a subquery's parameters with `sq<depth>_` so they never collide with the
outer query's parameters. A subquery param named `batch` becomes `:sq1_batch`, so the `Exec` param
map must use the prefixed key — see the mismatch that bites first-timers:

```go
// WRONG — the subquery expects sq1_batch, not batch
Exec(ctx, map[string]any{"batch": 100})

// RIGHT
Exec(ctx, map[string]any{"sq1_batch": 100})
```

When in doubt, call `Render()` and read `result.RequiredParams` — it lists the exact keys the
statement expects, prefixes and all.

## Wait policy

`SkipLocked()` and `NoWait()` chain after a lock mode (`ForUpdate`, `ForNoKeyUpdate`, `ForShare`,
`ForKeyShare`). They change what happens when a target row is already locked:

| Method         | Behavior on a locked row                          |
| -------------- | ------------------------------------------------- |
| *(default)*    | Wait until the lock is released                   |
| `SkipLocked()` | Skip the row — each worker gets a distinct batch  |
| `NoWait()`     | Error immediately instead of waiting              |

A wait policy without a lock mode is an error, surfaced when the query is rendered or executed.

## Subquery conditions

`WhereInSubquery` is one of four subquery WHERE methods available on `Select`, `Query`, `Modify`
(UPDATE), and `Remove` (DELETE):

| Method                        | SQL                       |
| ----------------------------- | ------------------------- |
| `WhereInSubquery(field, sub)` | `field IN (subquery)`     |
| `WhereNotInSubquery(field, sub)` | `field NOT IN (subquery)` |
| `WhereExists(sub)`            | `EXISTS (subquery)`       |
| `WhereNotExists(sub)`         | `NOT EXISTS (subquery)`   |

The subquery is any soy `Query` or `Select` builder, over the same table or a different one
(`WHERE user_id IN (SELECT id FROM users WHERE ...)`). On `Modify` and `Remove`, a subquery
condition satisfies the mandatory-WHERE safety guard, so a claim keyed solely on a subquery is
allowed.
